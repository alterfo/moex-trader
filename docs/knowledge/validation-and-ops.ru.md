# Инструменты валидации и эксплуатация live/sandbox

Прочитать перед правкой `cmd/strategyvalidation`, walk-forward, shadow reconciler, метрик/алертов, защит исполнения ордеров, kill switch или обвязки Telegram.

Дословно перенесено из AGENTS.md 2026-10-09; правила самого AGENTS.md по-прежнему приоритетнее.

## Инструменты валидации стратегии (2026-09-17)

- `docs/metrics.md` — журнал метрик; его формат проверяет `internal/metricsdoc` (`TestRepositoryMetricsDocumentPassesLint`), и ключевые числа должны оставаться на месте. Каждое число анализа записывается туда в том же коммите.
- Заморозка OOS: `artifacts/oos/freeze.json` фиксирует рецепт + `code_sha`; `cmd/oosfreeze -action status` сообщает дни сбора, сбрасываемые при смене хэша рецепта. Изменения кода носят только информационный характер — «любое изменение перезапускает счёт» проверяется вручную.
- Воспроизводимость walk-forward: `cmd/backtest -wf-dir` сохраняет модели по окнам и журналы решений (`internal/walkforward`).
- `cmd/strategyvalidation` печатает реестр попыток, deflated Sharpe и PBO. PBO вычисляется из сохранённых матриц `period_returns.csv` по окнам через `-returns-dirs`; шесть предрегистрированных попыток плана 2026-10-04 находятся в реестре, а PBO гейта развёртывания равен 0.1529 (см. `docs/metrics.md` «Deployment decision 2026-10 (Task 13)»).
- Отсев убыточных тикеров не помогает (`cmd/tickerselect`, `docs/metrics.md` 8.14): walk-forward отсев 4 худших тикеров по P&L прошлого блока не лучше отсева 4 случайных (p 0.77..0.91), P&L по тикерам не сохраняется между 91-дневными блоками (Спирмен -0.11), а in-sample вариант выглядит хорошо только из-за смещения отбора. Любой фильтр тикеров должен идти по правилу, не зависящему от P&L (ликвидность, волатильность), и оцениваться против распределения случайных отсевов.
- Очищенный (purged) walk-forward — стандарт валидации: `-embargo-bars 10` в `cmd/walkforward`, `cmd/backtest -wf-dir` и `cmd/trainmodel` (зеркально в `scripts/export_ensemble.py`) отбрасывает каждую обучающую строку, чей выход по метке попадает в тестовое окно, так что 10-дневная метка больше не пересекается между обучением и валидацией. Очищенный прогон — контроль гейта развёртывания.
- Паритет live и backtest: признаки строятся по закрытым барам, а `return_pct` берётся из закрытий свечей (`closedBarReturnPct`), а не из внутридневного `LastPrice`; shadow reconciler (`--shadow-digest`) пишет дайджест и помечает незакрытый последний бар или расхождение при повторном воспроизведении сигнала.
- Живая диагностика: предупреждения PSI-дрейфа (`risk.drift_psi_*`), circuit breaker по тикеру (`internal/risk/tickerbreaker.go`), гистерезис ребалансировки (`risk.rebalance_min_deviation_pct`) и двухопросный гистерезис сигнала подключены в `cmd/trader`. Breaker по тикеру отслеживает среднюю стоимость входа с комиссиями входа; комиссия входа не игнорируется.

## Заметки по эксплуатации live/sandbox

- Kill switch должен отменять только ордера по инструментам, которыми бот реально торгует (его собственный набор тикеров), — он никогда не должен трогать ручные ордера человека на том же счёте. (Регрессионный тест: `TestCancelOpenOrdersLeavesForeignOrdersAlone`, добавлен после обнаружения отмены посторонних ручных ордеров.)
- Бот отслеживает позиции только по собственным филлам — он не видит акций, которые человек держит вручную на том же счёте. Сигнал SELL по тикеру, который человек тоже держит вручную, будет истолкован как открытие шорта, а не «продажа акций человека». Это важно до подключения живого исполнения к счёту, на котором уже есть ручные позиции.
- Telegram: `api.telegram.org` напрямую из этой среды заблокирован — ходить через `telegram.proxy: "socks5://127.0.0.1:3333"`.
- Ночной вечерний дайджест (`telegram.daily_summary_enabled` + `daily_summary_time`, по умолчанию 19:05 MSK): после закрытия трейдер шлёт краткую сводку в Telegram — дневной P&L бота (реализованный за вычетом комиссий + изменение MTM открытых позиций, `internal/dailysummary`, учёт по средней стоимости зеркалирует `risk.TickerBreaker`), число филлов, дневное изменение IMOEX в % и долю настроенных тикеров, закрывшихся в плюс, — рыночный контекст для ручных лонг-позиций пользователя. Работает только внутри трейдера, держащего lease (дубля со standby нет); нерабочие дни (выходные/праздники) пропускаются по дате свечи IMOEX, так что нужен только конфиг, а не запись в cron. Развёрнутый `config.sandbox.yaml` включает его.
- RSS-лента Finmarket — Windows-1251, а не UTF-8 (`internal/ingestion/news/news.go` декодирует через `charset.NewReaderLabel`) — не считать каждую ленту UTF-8.
- **429 на RSS были из-за отсутствия `User-Agent`, а не реального ограничения частоты (2026-09-28).** `Fetcher.Fetch` отправлял UA Go по умолчанию `Go-http-client/1.1`; вживую проверено: vedomosti.ru отвечает 429 на 6/6 запросов с этим UA и 200 на 6/6 с браузерным UA. Исправлено установкой `newsUserAgent = "Mozilla/5.0 (compatible; moex-trader/1.0)"` (уже использовался `FetchTelegram`, теперь общий) на каждом RSS/JSON-запросе в `internal/ingestion/news/news.go`. Не добавлять прокси или платную ленту ради такого класса сбоев — сначала проверить UA.
- Обогащение AlgoPack молча отключается (одна строка в логе), когда `MOEX_TRADER_ALGOPACK_TOKEN` не задан, вместо записи 401 на каждый тикер в каждом цикле.
- Ордера защищены `TradingStatus` — бот проверяет, открыта ли сессия MOEX, перед отправкой, вместо того чтобы получать ошибку `30079` (`Instrument is not available for trading`) или тратить лимит API вне торгового времени.
- `risk.Gate.ApproveReason` (2026-09-19) возвращает `risk.Decision{Approved, Reason}`, а оркестратор теперь сохраняет причину отказа в payload аудита `risk_gate` (например, `{"approved":false,"reason":"fat_finger"}`). `Approve` остаётся делегирующей обёрткой, так что backtest и вызывающие, которым нужен только bool, не меняются. Причины тихих отказов: `kill_switch_active`, `ticker_breaker_blocked`, `drawdown_limit`, `max_lots_exceeded`, `max_position_exceeded`, `fat_finger`, `daily_loss`, `sector_cap`. При анализе отказов риск-гейта читать `reason` из `audit_events`, а не выводить из отсутствующего bool.
- Тяжёлые вычисления (обучение моделей, выгрузка датасета по многим тикерам: `cmd/exportdataset`, `cmd/trainmodel`, `cmd/calibrate`, `cmd/walkforward`, агрегация истории новостей) нужно запускать на ai-box (`ssh oleg@192.168.88.193`, репозиторий в `~/moex-trader` на той машине), а не на Mac. LAN IP ai-box указан в `peer_url` из `watchdog.yaml`; SSH-пользователь — `oleg`, а не обобщённый плейсхолдер `user`, используемый в других местах этого документа. Два параллельных запуска `exportdataset` (171%/157% CPU) однажды раскрутили Mac на полную; остановить через `pkill -f exportdataset` и перезапустить удалённо.
- Наблюдаемость (2026-10-04): `/metrics` отдаёт `moex_trader_inference_duration_seconds` (переименовано из прежнего `llm_inference_duration_seconds` — конвейер это модель, а не LLM), `signals_generated_total`, `risk_rejections_total{reason}`, `executor_skips_total{reason}`, `signal_probability`, `candle_age_seconds{ticker}`, `feature_psi{feature}`, `position_notional{ticker}`, `gross_exposure`, `lease_held`, а также только для мониторинга `var_95`/`var_99`/`es_95`/`es_99` (1-дневные VaR/ES книги по скользящим 250-дневным доходностям, `internal/risk/var.go`, одна строка в ежедневном дайджесте). Алерты Telegram ограничены cooldown (`internal/alert/telegram/watch.go`, конфиг `alerts.*`): коллапс вероятности, устаревшие свечи, превышение PSI. См. `docs/metrics.md` «Observability metrics and alerts (Task 6)».

## Драйверы сигнала в Reasoning (2026-10-18)

- `EnsembleSignalSource.Generate` дописывает ` drivers=<feature>:<±percentage points>` (топ-3 драйвера по окклюзии относительно обучающего среднего, `internal/model/explain.go`) после `ensemble:p=...`. Всё, что разбирает `Reasoning`, должно останавливаться на первом пробеле после `p=` (как делает `cmd/tailprecision`). Драйверы — описание верности модели, а не причинное утверждение; после любого переобучения проверять `go run ./cmd/explaincheck -dataset <h10.csv>`. Запущенному `./trader` нужна пересборка, чтобы они выводились.

## Paper-теневой трейдер (2026-10-18, одобрено владельцем)

Пока sandbox-трейдер отклоняется гейтом preflight (реализованный нетто за 90 дней -4859.13 при минимуме 1.00, см. `docs/metrics.md` «Preflight-concentration analysis»), развёрнутый `ensemble_model.json` работает в paper-режиме для сбора форвардных свидетельств: `config.paper.yaml` (копия `config.sandbox.yaml` с `broker: paper`, `is_paper_trading: true`, `preflight.enabled: false`, ежедневная сводка выключена), задача launchd `com.oleg.moex-trader.paper` (шаблон `scripts/launchd/com.oleg.moex-trader.paper.plist`, `KeepAlive`, бинарник `bin/trader-paper`, собранный из `./cmd/trader`, метрики на `:9092`). Он не размещает ордеров, не шлёт Telegram (в его окружении нет токена бота, `telegram alerts: enabled=false`) и имеет собственное состояние: `trader-paper.db`, `data/news_spool_paper.jsonl`, `artifacts/news_trades_paper.json`, `artifacts/incident_checks_paper.jsonl`, логи `~/Library/Logs/moex-trader-paper.{out,err}.log`. Гейт preflight отключён только в этом файле; в конфиге песочницы он по-прежнему включён, и paper-прогон не способ его обойти.

Первый цикл (воскресенье 2026-10-18, биржа закрыта): 17 тикеров прошли ingest, модель, риск-гейт и исполнитель, все HOLD, вероятности 0.355-0.606; несколько решений были отвергнуты защитой `out_of_range` (MTSS, GMKN, GAZP) — то же случайное вето, что описано в диагностике перекоса SELL.

Правило чтения, зафиксированное до появления данных: никаких выводов до 40 торговых дней и 100 закрытых сделок; затем сравнить реализованный P&L за вычетом комиссий и займа, hit rate и максимальную просадку с реплеем preflight в песочнице и с базовой линией «не торговать». Хороший форвардный результат — свидетельство для владельца, а не полномочие: он не меняет гейт, а прохождение критериев Task 13 по-прежнему обязательно для любой замены модели. Остановить: `launchctl bootout gui/$(id -u) ~/Library/LaunchAgents/com.oleg.moex-trader.paper.plist`. После изменения кода пересобрать `bin/trader-paper` и выполнить `launchctl kickstart -k gui/$(id -u)/com.oleg.moex-trader.paper`.
