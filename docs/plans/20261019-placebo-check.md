# Плацебо-проверка таблицы ridge: `cmd/placebocheck` (переписано 2026-10-19 вместо `cmd/synthcheck`)

Статус: план, критерии зафиксированы до реализации и до первого запуска. Реализацию ведёт одна сессия (правило 7 AGENTS.md: перед правкой `git status`).

## Почему не синтетические цены

Первый вариант (`cmd/synthcheck`, блочный бутстрап цен, прогон `EnsembleSignalSource`) проверял бы не ту модель: с 2026-10-19 боевой сигнал берёт `ScoreTableSource` из `data/ridge_scores.csv` (`score_table_path`), а таблица привязана к реальным датам и на синтетических ценах ничего не значит. Пересчитать ridge на синтетической панели можно только вместе со всей точечной панелью из 719 бумаг, это отдельный и дорогой шаг (вынесен в конец). Кроме того, независимые пути по тикерам разрушали корреляции между бумагами, а бутстрап убирает любую серийную структуру, поэтому «выброс в любую сторону» ничего не говорил о переобучении. Вместо этого плацебо работает на реальных ценах и реальной структуре книги и ломает только связь оценок с будущими доходностями.

## Что проверяем

Нулевая гипотеза: оценки таблицы не связаны с последующими доходностями; результат боевой книги (лонги и шорты, лимиты, издержки, заимствование) объясняется структурой книги (нетто-экспозиция, частота сделок, дрейф рынка). Статистика: реализованный P&L за вычетом заимствования на реплее.

Плацебо A, циклический сдвиг. Все тикеры сдвигаются на общее смещение k торговых дней по оси дат таблицы (хвост заворачивается в начало). Сохраняются распределение оценок, автокорреляция, одновременное поведение бумаг и число сделок; рвётся связь со временем.
Плацебо B, перестановка по срезу. На каждую дату оценки перемешиваются между тикерами (детерминированно от seed, номера прогона и даты). Сохраняется состав оценок в каждый день и общая нетто-экспозиция; рвётся выбор конкретных бумаг. Показывает, даёт ли P&L именно отбор, а не рыночную направленность книги.

Для A смещения |k| >= 21 (горизонт 21 бар), перебираются детерминированно, N = 200 различных k (если допустимых меньше 200, берутся все). Для B N = 200 прогонов, seed = 20261019 + номер.

## Окна и режимы

- W2, основное: 2025-03-05..2026-10-18 (вся накопленная таблица; оценки по построению внепробные).
- W1, описательно: окно гейта 2026-07-20..2026-10-18.
- Ставка заимствования в день: 0.00005 (принятый стресс) и 0.00047 (оценка РЕПО около 17% годовых, см. раздел о ставке в `docs/metrics.md`). Остальные параметры как у preflight: 17 бумаг, комиссия 0.0005, спред 0.0005, проскальзывание 0.0005, `target_notional` 15000, caps 90000 по нетто-лонгу и нетто-шорту, пороги 0.60/0.40.

## Критерий (до запуска)

Односторонний эмпирический p = (1 + число плацебо с P&L не ниже реального) / (N + 1), по W2 для каждой пары (плацебо, ставка).
- «Навык» засчитывается, если p <= 0.05 в обоих плацебо при ставке 0.00047.
- «Навык, ограниченный ставкой» — p <= 0.05 при 0.00005, но не при 0.00047.
- Иначе — «навык не отличим от структуры книги».
W1 и перцентили реального в распределении плацебо отчитываются без критерия. Результат не является gate и не меняет боевой контур; exit code 0 при успешном прогоне.
Оговорка: окна и гиперпараметры ridge (alpha 10, пересчёт раз в 63 дня, пороги 0.60/0.40) выбирались автором после просмотра этих данных, поэтому p-значения не поправлены на отбор и дают только верхнюю границу доверия.

## Реализация

1. `internal/placebo`: `Shift(table, k)`, `PermuteByDate(table, seed)` над структурой таблицы `internal/model.ScoreTable` (ключ тикер+дата, `p`), без записи на диск. Инварианты: общее смещение для всех тикеров; мультимножество оценок тикера сохраняется при сдвиге; мультимножество оценок даты сохраняется при перестановке; k = 0 даёт исходную таблицу.
2. `cmd/placebocheck` по образцу `cmd/strategyvalidation`, флаги: `-config`, `-score-table`, `-from`, `-till`, `-n` (200), `-borrow` (список, по умолчанию 0.00005,0.00047), `-seed`, `-workers`, `-out`. История свечей грузится один раз через `backtest.NewISSSource` и кладётся в in-memory `HistoricalSource`; прогон через существующий `backtest.NewEngine` с тем же `ScoreTableSource`, что у боевого пути (интерфейс `backtest.SignalSource` у него есть). Деньги только `decimal.Decimal`. Параллельность ограничена `-workers`.
3. Отчёт `reports/<дата>/placebo.json` и `.md`: параметры, реальный P&L, распределение плацебо (среднее, sd, квантили 5/50/95), p, число закрытых сделок реальной книги и плацебо, вердикт.
4. Тесты (stdlib testing, фейки, детерминизм): инварианты `internal/placebo`; e2e на `T.TempDir` с фейковым `HistoricalSource`: таблица-оракул, построенная по будущим доходностям, даёт p близко к минимуму 1/(N+1); случайная таблица даёт p без смещения (проверка по многим seed); повторный запуск с тем же seed даёт тот же отчёт.
5. До основного прогона замерить время одного прогона движка на W2 и записать в отчёт; N = 200 для четырёх сочетаний (плацебо x ставка) на двух окнах — около 1600 прогонов, при необходимости считать на ai-box.
6. Числа сразу в `docs/metrics.md` тем же коммитом (правило 8); проза и предостережения в `docs/knowledge/validation-and-ops.md`, строка в индексе знаний и упоминание рядом с `cmd/strategyvalidation`.

## Не делаем

Не трогаем preflight и живой путь; не добавляем секцию конфига (только флаги); не пишем в `ensemble_model.json`, `data/ridge_scores.csv` и не перезапускаем `./trader`; новых зависимостей нет.

## Отложенный этап: синтетическая панель

Если владелец захочет проверку на переобучение самого ridge: общий для всех тикеров стационарный блочный бутстрап лог-доходностей панели (`icaport.StationaryIndices`, средний блок 10 дней, одни индексы на все бумаги), пересчёт пяти сигналов и ridge на синтетической панели, затем реплей. Нужен предварительный замер стоимости пересчёта на 719 бумагах, N >= 200, критерии фиксируются отдельным дополнением до запуска. Дивидендные гэпы при этом переносить вместе с датами возвратных блоков нельзя: доходности брать полные (с дивидендами), как в шаге 25.
