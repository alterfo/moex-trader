# MOEX Multi-Agent Trader

## Обзор

Торговая система на Go для инструментов MOEX: собирает рыночные данные и новости, строит
`FeatureContext`, запрашивает у локальной LLM (Ollama) структурированный `TradeSignal`, пропускает его
через `RiskGate` и исполняет (сначала бумажно, затем живые микролоты через Tinkoff).
Каждый шаг записывается как `AuditEvent` для последующего разбора.

Архитектура — **однопроцессный модульный монолит** (внутренние Go-пакеты общаются
через интерфейсы, без сетевых переходов между компонентами) — по исходной спецификации это
меняет «модную мультиагентность» на надёжность, задержку и предсказуемость. Redis
Streams (Фаза 3) — необязательная внутренняя шина для последующего разделения процессов, а не
требование для работы системы.

Ни одной предыдущей Фазы 1 на диске нет — этот план проектирует её с нуля, затем
строит Фазы 2–4, как их изначально задал пользователь. Проект живёт в собственном репозитории
(`~/dev/fin/moex-trader`), отдельно от Python-проекта `finanalys`, который остаётся
несвязанным, нетронутым справочным источником идей (список тикеров, веса источников новостей) и только.

## Контекст (по результатам исследования)

- Соседний проект `finanalys` (`~/dev/fin/finanalys`) — Python-инструмент тональности новостей MOEX.
  Как код не используется — перенесены лишь его список из 21 инструмента (`config.py`

- CLI `ralphex` v1.6.1 установлен и будет выполнять этот план задача за задачей.

## Подход к разработке

- **Подход к тестированию**: обычный (сначала реализация, тесты сразу после, в той же
  задаче — не полноценный TDD).
- Каждую задачу завершать полностью, с проходящими тестами, до перехода к следующей.
- Один Go-модуль, пакет на область ответственности в `internal/`, тонкие точки входа в `cmd/`.
- Все денежные/ценовые значения используют `github.com/shopspring/decimal.Decimal` — никогда `float64`.
- SQLite (`modernc.org/sqlite`, чистый Go, без cgo) открывается с
  `?_journal_mode=WAL&_busy_timeout=5000`.
- Реальные внешние интеграции (живые ордера Tinkoff, Redis, Prometheus, Telegram,
  работа системы днями/неделями на реальных или бумажных деньгах) включены в задачи Фаз 3–4
  этого плана как *код* (клиент, обвязка, тесты на моках) — но получение учётных данных,
  развёртывание инфраструктуры и фактический запуск системы без присмотра — это
  пункты **После завершения**, а не чекбоксы, поскольку ни один агент этого сделать не может.
- **КРИТИЧНО: каждая задача ДОЛЖНА включать новые/обновлённые тесты.**
- **КРИТИЧНО: все тесты должны проходить до начала следующей задачи.**
- **КРИТИЧНО: обновлять этот файл плана при изменении объёма во время реализации.**

## Стратегия тестирования

- Юнит-тесты (`go test ./...`) для каждой задачи, табличные там, где это соответствует идиоматике Go.
- Внешние сервисы (Ollama, MOEX ISS, Tinkoff, Redis, Telegram) подменяются через
  `httptest.Server` / внутрипамятные заглушки — никаких реальных сетевых вызовов в тестах.
- UI нет, поэтому e2e/браузерных тестов нет.

## Технические детали

**Ядро домена (набросок):**
```go
type Action string
const (
    ActionBuy  Action = "BUY"
    ActionSell Action = "SELL"
    ActionHold Action = "HOLD"
)

type TradeSignal struct {
    Ticker     string
    Action     Action
    Confidence decimal.Decimal
    TargetLots int
    Reasoning  string
    GeneratedAt time.Time
}

type AuditEvent struct {
    ID        string // uuid v4
    Ticker    string
    Stage     string // "ingest" | "llm" | "risk_gate" | "executor"
    Payload   string // JSON blob
    CreatedAt time.Time
}
```

**DSN SQLite:** `file:trader.db?_journal_mode=WAL&_busy_timeout=5000`

**Конфиг (набросок YAML):**
```yaml
tickers: [SBER, YDEX, OZON, T, ...]   # ported from finanalys config.py
ollama:
  host: "<aibox-lan-ip>:11434"
  model: "qwen3.8"
  timeout: 10s
storage:
  path: "./trader.db"
is_paper_trading: true
poll_interval: 5m
```
