# Убрать LLM из критического пути живой торговли

## Обзор

Живой цикл решений `cmd/trader` сейчас синхронно вызывает LLM (Ollama)
на каждом тике: `Orchestrator.processTicker` → `orchestrator.LLMSignalSource` →
`llm.DecisionEngine.Generate` → сетевой обмен с Ollama → разбор JSON из
свободного ответа модели (`internal/orchestrator/orchestrator.go:210-220`,
`internal/orchestrator/llm_source.go`, `internal/llm/decision.go`). Из-за этого
критичный по риску путь недетерминирован, зависит от сети, медленный (
`DefaultSignalTimeout` равен 10 с, бэктест использует 90 с) и неаудируем в
обычном инженерном смысле (почему он сказал BUY?).

Этот план заменяет живой `SignalSource` **регуляризованной логистической
регрессией, обученной на собственной истории MOEX проекта на чистом Go**
(без Python, без ONNX — ограничение уровня ADR, см. «Подход к разработке»),
подключаемой в тот же самый шов `SignalSource`, который сейчас занимает
LLM. LLM остаётся только в офлайн-инструментах (`cmd/llmbench` и, при желании,
`cmd/backtest` для сравнения бок о бок) — после этого плана из `cmd/trader`
она полностью недостижима.

Поскольку `orchestrator.SignalSource` / `backtest.SignalSource` уже являются
швом интеграции (`Generate(ctx, domain.FeatureContext) (domain.TradeSignal,
error)`), а `domain.FeatureContext` уже несёт полный набор количественных признаков
(моментум, RSI, расстояние до MA, реализованная волатильность, z-оценка объёма,
дисбаланс стакана, тональность новостей), **изменения в `internal/risk` или в ядре
цикла `internal/orchestrator` не нужны** — план ограничен построением
нового источника сигнала и переподключением `cmd/trader`/`cmd/backtest`.

## Контекст (по результатам исследования)

- `internal/orchestrator/orchestrator.go`: интерфейс `SignalSource`,
  `Orchestrator.processTicker` вызывает `o.source.Generate(ctx, feature)` один раз на
  тикер за опрос — это место вызова перенаправляется, остальное без изменений.
- `internal/orchestrator/llm_source.go`: `LLMSignalSource` — адаптер, который
  заменяется для живого пути. `internal/llm/decision.go`,
  `internal/llm/prompt.go`, `internal/llm/client.go`, `internal/llm/schema.go`
  остаются нетронутыми (всё ещё используются `cmd/llmbench` и, при желании, `cmd/backtest`).
- `internal/domain/types.go`: `FeatureContext` (14 числовых полей сигнала кроме
  ticker/price/bid/ask — точный список, используемый как вектор признаков
  модели, см. «Технические детали») и `TradeSignal` (`Action`, `Confidence`,
  `TargetLots`, `Reasoning`, `HoldReason`). Константы `HoldReason*`
  (`HoldReasonModel`, `HoldReasonTimeout`, `HoldReasonInvalid`,
  `HoldReasonError`) должны сохранить сегодняшний смысл.
- `internal/features/builder.go` (`Builder.Build`) и
  `internal/features/price_features.go` (`ComputePriceFeatures`) вычисляют
  `FeatureContext` из `features.Input{Ticker, Price, Candles, News,
  OrderBookImbalance}`. **Важно**: `runTicker` из `internal/backtest/engine.go`
  строит `features.Input` только с `Ticker/Price/Candles` — без `News`, без
  `OrderBookImbalance` — потому что исторические новости/стакан не
  восстанавливаются. Значит, обучающие данные, порождённые проходом по истории,
  будут иметь `NewsSentiment == 0`, `NewsCount == 0`, `OrderBookImbalance == 0`
  в каждом образце. Обучение не должно ломаться на признаках с нулевой дисперсией (см.
  «Технические детали», защита стандартизации).
- `internal/backtest/engine.go`: интерфейс `SignalSource` (той же формы, что
  оркестраторный), `Engine.runTicker` идёт по `candles[minFeatureCandles:]`
  день за днём, строит признаки только из `candles[:d]` (без заглядывания вперёд), решает
  на `candles[d]`, исполняет по `candles[d+1].Open` (`decisionPrice`). Построитель
  обучающих данных и шаг валидации вне выборки оба переиспользуют этот
  движок/шаблон, а не изобретают параллельный.
- `internal/backtest/iss_source.go`: `ISSSource.History` получает полную историю
  дневных свечей (`interval=24`) из MOEX ISS с пагинацией. Это единственный
  источник исторических данных в репозитории — обучение берёт данные отсюда.
- `internal/config/config.go`: `Config.Ollama` (`Host`, `Model`, `Timeout`)
  сейчас обязателен в `Validate()`. Добавляется новая секция `Config.Model`
  (путь артефакта); `Ollama` перестаёт быть обязательным в центральном
  `Validate()`, так как теперь он необязателен/только офлайн — каждый бинарник, которому он ещё
  нужен (`cmd/llmbench`, `cmd/backtest` в режиме `-signal-source=llm`),
  делает собственную быструю проверку, повторяя существующий шаблон, где `cmd/trader`
  уже делает проверки, специфичные для брокера, сверх центральной валидации конфига.
- `cmd/trader/main.go`: строит `llmClient` → `decisionEngine` →
  `orchestrator.NewLLMSignalSource(...)` → передаётся как `Options.Source`. Это
  заменяемая обвязка.
- `cmd/backtest/main.go`: строит ту же цепочку LLM, обёрнутую в
  `backtest.NewRetryingSignalSource` и, при желании, `backtest.NewCachedSignalSource`,
  передаётся в `backtest.Config.SignalSource`. Получает флаг `-signal-source`
  (`model` по умолчанию, `llm` для сравнения) без поломки существующего
  LLM-пути.
- `risk.HardenedGate.Approve` (`internal/risk/gate.go`) уже обеспечивает
  `MaxLots`, полосы fat-finger, дневной убыток, просадку, kill switch — независимо
  от источника сигнала. Не трогается.
- Python в этом репозитории нигде нет — жёсткое правило проекта
  (`~/.claude/CLAUDE.md`: «больше никакого Python в проектах, только Go»).
  Зрелой Go-библиотеки для *обучения* градиентного бустинга нет
  (только библиотеки инференса вроде `leaves`, которым всё равно нужен Python/R для получения
  модели), поэтому градиентный бустинг в v1 исключён. Регуляризованная логистическая
  регрессия, обученная градиентным спуском, полностью реализуема на чистом Go
  и в любом случае устойчивее к переобучению, чем бустинговый ансамбль на скромной
  истории дневных баров по тикерам MOEX.

## Уже принятые решения (не пересматривать)

1. LLM полностью убрана из рантайма живой торговли — не оставлена как асинхронный/совещательный
   слой. Остаётся только в `cmd/llmbench` и, при желании, в режиме сравнения `cmd/backtest`.
2. Модель обучается на собственной истории MOEX проекта, а не на общей
   предобученной/фундаментальной модели (готового переносимого MOEX-альфа не существует;
   фундаментальные модели временных рядов в любом случае не выдают торговое действие).
3. Класс модели: **регуляризованная (L2) логистическая регрессия, чистый Go, обучение градиентным спуском.**
   Без ONNX, без подпроцесса Python, без внешней ML-библиотеки.
4. **Объединённая модель**: одна общая модель, обученная по всем настроенным тикерам
   (а не по модели на тикер) — больше обучающих строк, все поля `FeatureContext`,
   используемые как входы обучения, уже нормированы в проценты/z-оценки
   (а не сырые уровни цен), поэтому объединение по тикерам корректно; сама
   идентичность тикера в v1 не используется как признак (YAGNI — можно добавить позже
   как one-hot, если окажется, что нужен смещение по тикеру).
5. **Метка**: знак 5-дневной форвардной доходности от цены исполнения
   (`candles[d+1].Open`, в соответствии с существующим `decisionPrice` `backtest.Engine`),
   тот же горизонт, что у признака `Mom5d`. Строки, у которых форвардная доходность
   попадает в малую мёртвую зону (по умолчанию ±0.5%), исключаются из
   обучения как неоднозначные/шум, а не размечаются как HOLD — HOLD на инференсе
   возникает из собственной неопределённости модели (вероятность около 0.5), а не из
   третьего обучающего класса.

## Подход к разработке

- **Подход к тестированию**: обычный (реализация + тесты в одной задаче),
  как в `docs/plans/completed/20260915-commissions-and-finam-broker.md`.
- Все денежные поля остаются `decimal.Decimal`; векторы признаков для модели — `float64`
  (стандарт для численной оптимизации) — конвертировать на границе
  `FeatureContext`, не раньше.
- **Никакого заглядывания вперёд**: любая функция, строящая обучающий вектор признаков
  для дня решения `d`, должна видеть только `candles[:d]` (та же дисциплина, что у
  `backtest.Engine.runTicker`). Метки вычисляются из `candles[d+1:d+1+horizon]`
  и используются только как обучающая цель, никогда как признак.
- **Walk-forward разбиение, а не случайное**: единая глобальная дата отсечения
  делит образцы всех тикеров на обучение (до отсечения) и валидацию
  (с отсечения). Оставить зазор в `horizon` торговых дней перед отсечением, чтобы
  окно форвардной доходности ни одной обучающей метки не заходило в период
  валидации (утечка на границе).
- **КРИТИЧНО: каждая задача ДОЛЖНА включать новые/обновлённые тесты.**
- **КРИТИЧНО: все тесты должны проходить до начала следующей задачи.**
- **КРИТИЧНО: обновлять этот файл плана при изменении объёма во время реализации.**

## Стратегия тестирования

- Юнит-тесты для каждой задачи. Реальных сетевых вызовов нет — вызовы `ISSSource`/MOEX ISS в тестах
  идут через `httptest.Server` или внутрипамятный поддельный
  `backtest.HistoricalSource`, по соглашениям тестов пакета `backtest`
  (`internal/backtest/engine_test.go`).
- Тренер тестируется на синтетических разделимых данных (признак с
  известной связью знака с меткой) с детерминированным порогом точности —
  а не на реальных данных MOEX в юнит-тестах.
- Сквозной конвейер обучения (`cmd/trainmodel`) тестируется на небольшой
  синтетической/фикстурной серии свечей, а не на живых данных MOEX (это
  ручной шаг «После завершения»).

## Технические детали

**Вектор признаков модели (фиксированный порядок, `internal/model/features.go`
`ToVector`)** — все 14 неценовых полей `domain.FeatureContext`:
`ReturnPct, RealizedVolatility, NewsSentiment, NewsCount, OrderBookImbalance,
Mom5d, Mom21d, Mom63d, Reversal1d, RSI14, DistMA20Pct, DistMA50Pct,
RealizedVol21d, VolumeZScore20d`. `Ticker`/`GeneratedAt`/`LastPrice`/`PrevClose`/
`Bid`/`Ask` исключены — они нестационарны/несопоставимы между тикерами и
временем, а именно это делает объединение корректным.

**Почему `NewsSentiment`/`NewsCount`/`OrderBookImbalance` обучатся до веса ~0**:
конвейер обучения строит признаки так же, как сегодня
`backtest.Engine.runTicker` — без исторического воспроизведения новостей и
стакана. Эти три колонки будут константой (0) в
каждой обучающей строке, поэтому после стандартизации (с защитой, см. Задачу 1) их
выученный коэффициент остаётся около начального (малого, регуляризованного) значения и
не вносит практически ничего в обученную модель. При инференсе в живом рантайме эти
поля *будут* заполняться `orchestrator.NewMOEXIngestor`/AlgoPack, так что
модель технически их «видит», но никогда не обучалась ими пользоваться. Это
известное задокументированное ограничение v1, а не баг — будущая итерация могла бы построить
историческое воспроизведение новостей/стакана, чтобы реально обучаться на них.

**Отображение метки / вероятности**: бинарная логистическая регрессия предсказывает `P(5-дневная
форвардная доходность > 0)` на строках вне мёртвой зоны. На инференсе: `p >= BuyThreshold
(0.55)` → BUY, `p <= SellThreshold (0.45)` → SELL, иначе HOLD. Эта асимметричная
мёртвая зона вокруг 0.5 мешает модели торговать по предсказанию «орёл или решка» —
это прямой аналог мёртвой зоны обучения, применённый во время
решения, а не во время разметки.

**Размер позиции**: `TargetLots = MaxLots` (из `risk.Config.MaxLots`/`cfg.Risk.MaxLots`)
для любого BUY/SELL — плоский размер позиции, как в типичном использовании существующего пути LLM и
лимитах семейства единичного лота `risk.HardenedGate`. Взвешивания размера по уверенности
в v1 нет (YAGNI; риск-гейт — авторитет по размеру/безопасности, а не источник сигнала).

**Переобучение `model.json`**: в v1 нет автоматического расписания переобучения или триггера
дрейфа. Чтобы обновить живой артефакт, запустить
`go run ./cmd/trainmodel -config config.yaml` (при желании переопределив
`-tickers`, `-from`, `-till` или `-out`), изучить напечатанный отчёт валидации
вне выборки и перезапускать `cmd/trader` только если Sharpe/доля верных/максимальная
просадка приемлемы для текущего режима MOEX.

## После завершения

**Ручная проверка** (обязательна до переключения `is_paper_trading: false`
с этой моделью в цикле):
- Запустить `cmd/trainmodel` на реальной истории MOEX для фактически настроенных
  тикеров и изучить напечатанные Sharpe/долю верных/максимальную просадку на валидации —
  автоматического гейта «прошло/не прошло» в этом плане нет; решает человек,
  достаточно ли метрики хороши для торговли.
- Запустить `cmd/backtest -signal-source=model` бок о бок с
  `-signal-source=llm` на том же окне и сравнить отчёты `Result.Markdown()`.
- Периодически перезапускать `cmd/trainmodel` (в v1 без автоматизации) по мере смены режима MOEX;
  в этом плане нет обнаружения дрейфа/триггера переобучения.

**Обновления внешних систем**:
- Нет — всё целиком внутри репозитория; потребляющие проекты,
  конфигурации развёртывания и сторонние интеграции не меняются.
