## Подход к разработке

- **Подход к тестированию**: обычный (сначала код, затем тесты в той же задаче).
- Каждую задачу завершать полностью до перехода к следующей; небольшие целевые коммиты.
- **Каждая задача ДОЛЖНА включать новые/обновлённые тесты** для изменений кода, покрывающие
  пути успеха и ошибки. Все тесты должны проходить до следующей задачи.
- Обновлять этот план при изменении объёма.
- Правила проекта, применимые к каждой задаче:
  - никаких комментариев в коде (правило пользователя);
  - деньги — `decimal.Decimal`, никогда `float64`;
  - каждое новое или изменённое число попадает в `docs/metrics.md` **тем же
    коммитом** (инцидент E4), а `TestRepositoryMetricsDocumentPassesLint` должен
    проходить;
  - общее рабочее дерево с другой сессией: проверять `git status` перед
    правкой, коммитить быстро (правило 7 AGENTS.md);
  - тяжёлые вычисления (`cmd/exportdataset`, `cmd/trainmodel`, `cmd/walkforward`,
    обучение `scripts/export_ensemble.py`) выполняются на ai-box
    (`ssh oleg@192.168.88.193`, репозиторий `~/moex-trader`), никогда на Mac;
  - новые флаги по умолчанию соответствуют текущему поведению; в живом рецепте
    ничего не меняется до Задачи 13.
- Обратная совместимость: существующие флаги CLI, ключи конфига, стадии аудита и
  раскладки каталогов walk-forward продолжают работать.

## Стратегия тестирования

- Юнит-тесты для каждой задачи (табличные там, где это подходит стилю пакета).
- Golden-бэктест (Задача 1) — регрессионный гейт для всех последующих задач: любая
  задача, меняющая его вывод непреднамеренно, неверна.
- UI нет, e2e-набора нет.

## Технические детали

### Гейт развёртывания (предрегистрирован 2026-10-04, не править после начала Задачи 5)

Вариант можно развёртывать, только если **все** условия выполнены относительно контроля Задачи 5, на
тех же 6 квартальных purged-окнах (`-embargo-bars 10`), депозит 1M, издержки
0.0005 комиссия + 0.0005 спред + 0.0005 проскальзывание, kill switch включён:

1. суммарный **реализованный** P&L > контроля (MTM никогда не считается);
2. реализованный P&L ≥ контроля минимум в 4 из 6 окон;
3. максимальная просадка ≤ 3% в каждом окне и kill switch ни разу не срабатывает;
4. для изменений меток/обучения (A, B, C): средний val AUC не ниже контроля больше
   чем на 0.005;
5. PBO по полному реестру попыток этого плана < 0.5;
6. 90-дневный preflight проходит с кандидатом.

DSR сообщается для каждого варианта, но **не** является критерием развёртывания здесь —
DSR > 0.95 остаётся планкой выхода на реальные деньги, без изменений.

### Форматы

- `period_returns.csv`: `date,realized_net` (десятичная строка), одна строка на
  торговый день окна.
- Множитель волатильности: `clamp(median_σ / σ_i, min_mult, max_mult)`, σ из признака
  `realized_volatility` того же бара.
- Проверка сектора: `Σ_{t∈sector, t≠ticker} |notional_t| + |notional_ticker after
  order| ≤ cap`.
