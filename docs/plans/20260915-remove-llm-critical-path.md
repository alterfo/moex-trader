# Remove LLM From the Live Trading Critical Path

## Overview

`cmd/trader`'s live decision loop currently calls an LLM (Ollama) synchronously
on every tick: `Orchestrator.processTicker` → `orchestrator.LLMSignalSource` →
`llm.DecisionEngine.Generate` → network round-trip to Ollama → JSON parse of a
free-form model response (`internal/orchestrator/orchestrator.go:210-220`,
`internal/orchestrator/llm_source.go`, `internal/llm/decision.go`). This makes
the risk-critical path non-deterministic, network-dependent, slow (the
`DefaultSignalTimeout` is 10s, backtest uses 90s), and unauditable in the
normal engineering sense (why did it say BUY?).

This plan replaces the live `SignalSource` with a **regularized logistic
regression model, trained on the project's own MOEX history in pure Go**
(no Python, no ONNX — ADR-level constraint, see Development Approach), plugged
into the exact same `SignalSource` seam the LLM currently occupies. The LLM
stays only in offline tooling (`cmd/llmbench`, and optionally `cmd/backtest`
for side-by-side comparison) — it is fully unreachable from `cmd/trader` after
this plan.

Because `orchestrator.SignalSource` / `backtest.SignalSource` are already the
integration seam (`Generate(ctx, domain.FeatureContext) (domain.TradeSignal,
error)`), and `domain.FeatureContext` already carries a full quant feature set
(momentum, RSI, distance from MA, realized vol, volume z-score, order book
imbalance, news sentiment), **no changes are needed in `internal/risk` or
`internal/orchestrator`'s core loop** — this plan is scoped to building the
new signal source and rewiring `cmd/trader`/`cmd/backtest` to use it.

## Context (from discovery)

- `internal/orchestrator/orchestrator.go`: `SignalSource` interface,
  `Orchestrator.processTicker` calls `o.source.Generate(ctx, feature)` once per
  ticker per poll — this is the call site being repointed, unchanged otherwise.
- `internal/orchestrator/llm_source.go`: `LLMSignalSource` — the adapter being
  replaced for the live path. `internal/llm/decision.go`,
  `internal/llm/prompt.go`, `internal/llm/client.go`, `internal/llm/schema.go`
  stay untouched (still used by `cmd/llmbench` and optionally `cmd/backtest`).
- `internal/domain/types.go`: `FeatureContext` (14 numeric signal fields besides
  ticker/price/bid/ask — see Technical Details for the exact list used as the
  model's feature vector) and `TradeSignal` (`Action`, `Confidence`,
  `TargetLots`, `Reasoning`, `HoldReason`). `HoldReason*` constants
  (`HoldReasonModel`, `HoldReasonTimeout`, `HoldReasonInvalid`,
  `HoldReasonError`) must keep meaning what they mean today.
- `internal/features/builder.go` (`Builder.Build`) and
  `internal/features/price_features.go` (`ComputePriceFeatures`) compute
  `FeatureContext` from `features.Input{Ticker, Price, Candles, News,
  OrderBookImbalance}`. **Important**: `internal/backtest/engine.go`'s
  `runTicker` builds `features.Input` with only `Ticker/Price/Candles` — no
  `News`, no `OrderBookImbalance` — because historical news/order-book replay
  isn't reconstructed. That means training data generated by walking history
  will have `NewsSentiment == 0`, `NewsCount == 0`, `OrderBookImbalance == 0`
  for every sample. The trainer must not choke on zero-variance features (see
  Technical Details, standardization guard).
- `internal/backtest/engine.go`: `SignalSource` interface (identical shape to
  the orchestrator one), `Engine.runTicker` walks `candles[minFeatureCandles:]`
  day by day, builds features from `candles[:d]` only (no lookahead), decides
  at `candles[d]`, executes at `candles[d+1].Open` (`decisionPrice`). The new
  training-data builder and the out-of-sample validation step both reuse this
  engine/pattern rather than inventing a parallel one.
- `internal/backtest/iss_source.go`: `ISSSource.History` fetches full daily
  candle history (`interval=24`) from MOEX ISS, paginated. This is the only
  historical data source in the repo — training pulls from here.
- `internal/config/config.go`: `Config.Ollama` (`Host`, `Model`, `Timeout`) is
  currently required by `Validate()`. A new `Config.Model` section
  (artifact path) is added; `Ollama` becomes non-required in central
  `Validate()` since it's now optional/offline-only — each binary that still
  needs it (`cmd/llmbench`, `cmd/backtest` in `-signal-source=llm` mode) does
  its own fail-fast check, matching the existing pattern where `cmd/trader`
  already does broker-specific checks beyond central config validation.
- `cmd/trader/main.go`: builds `llmClient` → `decisionEngine` →
  `orchestrator.NewLLMSignalSource(...)` → passed as `Options.Source`. This is
  the wiring being replaced.
- `cmd/backtest/main.go`: builds the same LLM chain, wrapped in
  `backtest.NewRetryingSignalSource` and optionally `backtest.NewCachedSignalSource`,
  passed to `backtest.Config.SignalSource`. Gains a `-signal-source` flag
  (`model` default, `llm` for comparison) without breaking the existing LLM
  path.
- `risk.HardenedGate.Approve` (`internal/risk/gate.go`) already enforces
  `MaxLots`, fat-finger bands, daily loss, drawdown, kill switch — independent
  of signal source. Not touched.
- No Python anywhere in this repo — hard project rule
  (`~/.claude/CLAUDE.md`: "Python в проектах больше не используем — только
  Go"). No mature Go library exists for *training* gradient boosting models
  (only inference libs like `leaves`, which still need Python/R to produce the
  model), so gradient boosting is out for v1. A regularized logistic
  regression trained via gradient descent is fully implementable in pure Go
  and is more robust to overfitting than a boosted ensemble on MOEX's modest
  per-ticker daily-bar history anyway.

## Decisions Already Made (do not re-litigate)

1. LLM fully removed from the live runtime path — not kept as an async/advisory
   layer. Stays only in `cmd/llmbench` and optionally `cmd/backtest` comparison
   mode.
2. Model is trained on the project's own MOEX history, not a generic
   pretrained/foundation model (no transferable MOEX alpha exists off the
   shelf; time-series foundation models don't emit a trading action anyway).
3. Model class: **regularized (L2) logistic regression, pure Go, trained via
   gradient descent.** No ONNX, no Python subprocess, no external ML library.
4. **Pooled model**: one shared model trained across all configured tickers
   (not one model per ticker) — more training rows, all `FeatureContext`
   fields used as training inputs are already percentage/z-score normalized
   (not raw price levels), so pooling across tickers is valid; ticker identity
   itself is not used as a feature in v1 (YAGNI — can be added later as a
   one-hot if a ticker-specific bias turns out to matter).
5. **Label**: sign of 5-trading-day forward return from the execution price
   (`candles[d+1].Open`, matching `backtest.Engine`'s existing
   `decisionPrice`), same horizon as the existing `Mom5d` feature. Rows whose
   forward return falls inside a small deadband (default ±0.5%) are excluded
   from training as ambiguous/noise, not labeled HOLD — HOLD at inference time
   comes from the model's own uncertainty (probability near 0.5), not from a
   third training class.

## Development Approach

- **Testing approach**: Regular (implementation + tests in the same task),
  matching `docs/plans/completed/20260915-commissions-and-finam-broker.md`.
- All money fields stay `decimal.Decimal`; feature vectors for the model are
  `float64` (standard for numerical optimization) — convert at the
  `FeatureContext` boundary, not before.
- **No lookahead, ever**: any function that builds a training feature vector
  for decision day `d` must only see `candles[:d]` (identical discipline to
  `backtest.Engine.runTicker`). Labels are computed from `candles[d+1:d+1+horizon]`
  and used only as the training target, never as a feature.
- **Walk-forward split, not random split**: a single global cutoff date
  divides all tickers' samples into train (before cutoff) and validation
  (cutoff onward). Leave a gap of `horizon` trading days before the cutoff so
  no training label's forward-return window crosses into the validation
  period (boundary leakage).
- **CRITICAL: every task MUST include new/updated tests.**
- **CRITICAL: all tests must pass before starting next task.**
- **CRITICAL: update this plan file when scope changes during implementation.**

## Testing Strategy

- Unit tests for every task. No real network calls — `ISSSource`/MOEX ISS
  calls in tests go through `httptest.Server` or an in-memory fake
  `backtest.HistoricalSource`, matching existing `backtest` package test
  conventions (`internal/backtest/engine_test.go`).
- The trainer is tested against synthetic separable data (a feature with a
  known sign relationship to the label) with a deterministic accuracy
  threshold — not against real MOEX data in unit tests.
- The end-to-end training pipeline (`cmd/trainmodel`) is tested with a small
  synthetic/fixture candle series, not live MOEX data (that's a
  Post-Completion manual step).

## Technical Details

**Model feature vector (fixed order, `internal/model/features.go`
`ToVector`)** — all 14 non-price fields of `domain.FeatureContext`:
`ReturnPct, RealizedVolatility, NewsSentiment, NewsCount, OrderBookImbalance,
Mom5d, Mom21d, Mom63d, Reversal1d, RSI14, DistMA20Pct, DistMA50Pct,
RealizedVol21d, VolumeZScore20d`. `Ticker`/`GeneratedAt`/`LastPrice`/`PrevClose`/
`Bid`/`Ask` are excluded — they're not stationary/comparable across tickers or
time, which is what makes pooling valid.

**Why `NewsSentiment`/`NewsCount`/`OrderBookImbalance` will train to ~0
weight**: the training pipeline builds features the same way
`backtest.Engine.runTicker` does today — no historical news replay, no
historical order-book replay. These three columns will be constant (0) in
every training row, so after standardization (guarded, see Task 1) their
learned coefficient stays near its (small, regularized) initial value and
contributes ~nothing to the trained model. At live-runtime inference these
fields *will* be populated by `orchestrator.NewMOEXIngestor`/AlgoPack, so the
model technically "sees" them but was never trained to use them. This is a
known, documented v1 limitation, not a bug — a future iteration could build a
historical news/order-book replay to actually train on them.

**Label / probability mapping**: binary logistic regression predicts `P(5-day
forward return > 0)` on non-deadband rows. At inference: `p >= BuyThreshold
(0.55)` → BUY, `p <= SellThreshold (0.45)` → SELL, else HOLD. This asymmetric
dead zone around 0.5 is what prevents the model from trading on a coin-flip
prediction — it's the direct analog of the training deadband, applied at
decision time instead of label time.

**Sizing**: `TargetLots = MaxLots` (from `risk.Config.MaxLots`/`cfg.Risk.MaxLots`)
for any BUY/SELL — flat position sizing, matching the existing LLM path's
typical usage and `risk.HardenedGate`'s single-lot-family limits. No
confidence-weighted sizing in v1 (YAGNI; the risk gate is the sizing/safety
authority, not the signal source).

**Retraining `model.json`**: v1 has no automated retraining schedule or drift
trigger. To refresh the live artifact, run
`go run ./cmd/trainmodel -config config.yaml` (optionally overriding
`-tickers`, `-from`, `-till`, or `-out`), inspect the printed out-of-sample
validation report, and restart `cmd/trader` only if the Sharpe/hit-rate/max
drawdown are acceptable for the current MOEX regime.

with this model in the loop):
- Run `cmd/trainmodel` against real MOEX history for the actual configured

  shifts; there's no drift-detection/retraining trigger in this plan.

- None — this is entirely internal to the repo; no consuming projects,
